# AI 辅助等待验收

日期：2026-09-24。目标设备：fnOS x86_64，192.168.3.7。受控范围仅为 Bot 与 test/毒药💊私聊；未测试群聊、ARM64 实机或 FPK 应用中心安装。

## 行为与本地校验

- 系统设置将原接续方式下拉改为默认开启的开关，默认等待 5 分钟；可修改分钟数。说明明确每次人工回复后，首次自动回复按首条新来信开始等待，同一轮后续来信不延长；该轮首次成功自动回复后，后续按原节奏；再次人工回复重新开始。
- 关闭时保存保留分钟数；对实际人工回复，仅关闭对应联系人的自动回复并持久化，不关闭全局或其它联系人。AI 自发消息不会视为人工接管。
- `node --test test/ai-takeover-wait.test.mjs`：9/9 通过，覆盖私聊与群聊规则、首条来信计时、后续来信不重置、再次人工回复、只关闭目标、重新开启、单次等待、重启和 uncertain 防重发。
- `npm run test:ai-ui`：AI 助手浏览器回归通过，包含默认开启/5分钟、关闭保存与保留时长、修改时长和说明文案。
- `npm run check` 通过。`npm test`：717 项，716 通过、0 失败、1 项既有跳过。

## 真机证据

设备代码热部署前备份了服务模块、前端文件及 Bot/test AI 配置，备份目录为 `/vol1/@appdata/qibox/upgrade-backups/ai-wait-switch-20260924-predeploy/`。设置界面实际显示开关、说明和分钟输入框；关闭保存后界面提示成功，分钟字段保留且禁用。截图：`device-ui-settings.png`、`device-ui-disabled.png`。

受控 Bot 手动回复后，test 发出带 `AIWAIT-` 标记的新来信。首轮接口记录 `startedAt=1790241538226`、`dueAt=1790241598226`；阈值前没有增加已发送数。Bot 后续真实回复的聊天时间戳为 `1790241668`，约晚于阈值 70 秒（模型生成及原生发送耗时），来信聊天时间戳为 `1790241522`。所以证据表明阈值前未发、到期后实际发出；不代表精确的 7 秒延迟。

随后独立来信无分钟级等待并真实收到 Bot 回复（test 聊天时间 `1790242088`，Bot 回复 `1790242131`）。一条先前 delivery 状态为 uncertain 的消息没有补发；先检查原生聊天及记录，再发送了不同的独立标记消息用于正常节奏复测。

第二次 Bot 手动回复后，首条独立来信重新计时：`startedAt=1790242292005`、`dueAt=1790242352005`，阈值前未发；Bot 实际回复聊天时间戳 `1790242377`，API 随后记录 `replied`，等待清除，已发送数增加。该次真实回复约晚于阈值 25 秒。

关闭分支通过真实 UI 保存为关闭后，Bot 手动回复触发 `auto-reply-disabled`；毒药联系人的 `replyEnabled=false` 且未选中，原 15 个其它目标和全局回复开关仍保持开启。test 随后发送了独立来信，Bot 未自动回复。

上述聊天时间戳按设备聊天记录原样记载（秒）；`startedAt`/`dueAt` 按接口毫秒值记载。测试期间产生的 `AIWAIT-` 原生聊天消息保留在 Bot 与 test 的受控私聊中，以便核验；没有删除这些微信聊天消息或向其它联系人发消息。

测试后恢复 Bot 的原 15 个已选目标及其 ID 集合、毒药原关闭且未选择的 profile、`takeover={enabled:true,minutes:5}`、`globalReply=true`，以及 test 的原 AI 配置（字节哈希与备份一致）。恢复后再次核验通过。
