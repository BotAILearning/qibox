# 分析报告：语音、图片与视频分析方案

状态：0.9.40-debug.004 已在 fnOS x86_64 真机通过页面、语音、图片、视频与完整报告链路验收；ARM64 运行时已打包，尚未在 ARM64 硬件安装。

## 用户操作

在电脑端「分析报告」的分析要求与时间范围之间增加一组「加入分析的内容」，保留现有联系人、分析方向和日期选择：

```text
加入分析的内容
□ 分析语音          使用本地微信的转文字能力；会打开相应聊天，语音较多时需要更长时间。
□ 分析图片和视频    本地读取图片、将视频抽成关键帧；需要所选模型支持图片输入。
```

两项默认关闭、相互独立。本次提交时固定选项和日期范围，队列中的每位联系人使用同一组选择。关闭时，语音、图片、视频仅作为未解析的消息类型存在，模型不能从占位符猜测内容。开启后仍只分析实际成功解析的媒体；报告明确列出成功、跳过和受容量限制的数量。设置保留在当前页面草稿，切换微信账号/实例时清空，不把上次勾选悄悄带给另一账号。

勾选「图片和视频」时先提示“需要所选模型支持图片输入，可能增加模型费用”。第一批真实图片请求会验证模型的图片输入能力；若明确不支持，则后续批次跳过，继续文字和已选语音分析，并提示可在下次更换模型。不得把模型拒绝图片后自动降级为文字，却仍标示图片/视频已分析。勾选「语音」时提示本地微信逐条转文字可能较慢，具体耗时随条数变化。

## 数据和模型处理

1. 仍按当前账号、联系人和用户选择的时间范围读取一次有序聊天记录。为每条消息保留 ID、方向、时间和类型。媒体预处理只针对最终进入本次报告材料的消息；若文字材料因容量裁剪，媒体范围也随之收缩，并在覆盖提示中列明。
2. 语音：先确认目标语音处于该联系人最近的微信消息范围，再用已验证的本地微信导航打开聊天，按消息 ID 调用微信「转文字」。原生能力还要求该语音气泡在当前可见区域且能与旁边文字唯一对应；无法安全定位的旧语音跳过，不猜测位置或点击。得到真实转写后替换本次分析材料中的 `[语音]`，保留 `source=wechat`。没有转写的语音不得当作文字事实。
3. 图片：通过现有本地附件读取通道按消息 ID 与原消息秒级时间戳获取；只接受受支持的图片格式和大小，验证账号及联系人归属。图片本身不写入报告历史。
4. 视频：增加按消息 ID 与原消息秒级时间戳绑定的本地附件解析通道；从该消息的 XML 读取文件字节数及 MD5，只在当前微信账号的本地视频缓存与当前联系人附件目录中查找，先以精确字节数缩小候选，再对整个文件计算 MD5 并与消息校验值相等后使用。文件名不等于视频内容 MD5；不能依赖 XML 路径、网址或模糊时间匹配。用随应用打包的本地解码器检查格式/时长后，在约 10%、50%、80% 时间点各取一帧，缩放成受模型支持的 JPEG。每帧带原视频消息 ID 和相对时间。视频音轨不在本选项内处理，报告应称“视频画面”。
5. 图片和视频帧以最多三张一批送入所选视觉模型，先生成结构化、克制的画面描述，再与真实语音转写及文字消息按原消息顺序组成最终报告材料。模型描述标记为“图像/视频画面识别结果”，不能伪装成聊天原文；图片里的指令视为资料，不改变分析规则。最终报告模型仍须遵守实际覆盖、统计来源和不编造事实的约束。
6. 最终报告只保存正文、用户选择范围、实际覆盖范围和各类媒体的处理统计；不保存原始附件、帧、转写缓存或中间模型请求。历史查看和导出只读已保存快照，不重新解析媒体。

## 数量、等待和重试

以下是实现初始资源预算，须经 fnOS 真机容量测试调整。页面在选择选项时提示耗时与模型要求；开始读取聊天后按阶段展示实际处理条数，完成后列出超出上限的数量：

| 项目 | 初始预算 | 单项等待 | 失败处理 |
| --- | --- | --- | --- |
| 微信语音转文字 | 本次最多 12 条，逐条执行 | 25 秒 | 可恢复的超时/临时失败再试 1 次，间隔约 2 秒 |
| 图片读取 | 本次最多 6 张 | 每张 40 秒（包括微信数据库冷启动） | 临时读取失败再试 1 次 |
| 视频解析 | 本次最多 3 段，每段最多 3 帧；单源文件不超过 100 MB、10 分钟 | 每段 42 秒（含附件定位与解码） | 临时解码失败再试 1 次 |
| 视觉模型批次 | 每次最多 3 张图/帧 | 使用模型设置的超时，最高 90 秒 | 仅对超时、限流和服务端临时错误再试 1 次 |

配额优先选取本次实际材料里较新的消息，最终仍按原时间顺序组织分析；超额项计入“容量限制未解析”。媒体预处理还需设置约 20 分钟的整体验证期限，期限将至便跳过剩余媒体并继续最终报告，使单联系人请求留在当前 30 分钟客户端等待范围内。超时应确实中止对应子操作，不能只让页面继续而在后台无限运行。读取损坏、身份不符、媒体不存在、模型明确不支持、用户取消和账号变化不重试；账号变化或取消直接停止本次任务，其他单项失败用明确原因计数并继续下一条。最终文字分析失败仍按现有报告失败处理，不能输出一份貌似成功的空报告。

## 进度与结果

页面显示当前联系人及阶段：读取聊天 → 语音转文字 → 读取图片 → 视频抽帧 → 图片/视频理解 → 生成报告。每阶段显示“已处理/总数、成功、已跳过”，并显示当前第几次尝试；完成一条就更新一次，长等待时仍显示当前媒体类型及已等待时间。进度使用服务端操作状态轮询，不展示原始聊天或附件缩略图。用户取消后停止后续媒体与模型请求；队列中已成功保存的其他联系人报告不回滚。

报告顶部及历史快照保留一行覆盖摘要，例如“语音 8 条：转写 6、跳过 2；图片 4 张：识别 3、跳过 1；视频 2 段：抽帧 1、跳过 1”。未勾选的类型写“未选择分析”，不把占位消息算成已理解的内容。现有“分析条数”应拆分为“记录条数”和“内容已解析条数”，避免把 `[语音]`、`[图片]`、`[视频]` 误报为已分析内容。
