# 栖盒体验与性能优化验收基线

本轮由用户在 2026-10-02 明确启动。基于真机 0.10.20-stable.003 和对应源代码推进，范围为 fnOS；保留所有已支持功能、账号隔离和人工接管规则。以下指标是验收目标，不能用未完成的测试替代结论。

## 体验最高标准与实现方向

| 方面 | 标准 | 优化及验收方法 |
| --- | --- | --- |
| 页面可理解性 | 主任务、当前账号、保存状态一眼可见；选填内容不造成任务压力 | 个人信息紧凑分组；已有内容直接预览；常驻保存入口；不把填写率当成必须完成的任务 |
| 操作效率 | 常用任务就地完成；无重复填写和无效确认 | 保留未保存草稿、字段级编辑与分享、搜索直达联系人；不增加新流程 |
| 无障碍与适配 | 自有控件键盘可达、焦点可见、标签明确；目标符合 WCAG AA；触摸目标至少 44px | 320/390/1024/1440 布局检查，无横向溢出；键盘及表单错误检查。截图检查不等同完整无障碍认证 |
| 功能完整性 | 微信输入、复制粘贴、拖拽文件、图片、聊天、文章、窗口操作保持可用 | 独立记录真实微信操作结果；系统对话框、剪贴板回传、中文与 emoji 必须验证 |
| 反馈与恢复 | 本地操作即时反馈；长任务显示阶段，可取消；失败留草稿，可重试 | 控件反馈目标 100ms；取消不继续占用扫描；网络断开后能重连，不重复发送 |
| 运行性能 | 集成层不因联系人或扫描范围增长而产生无界分配；交互不被后台工作阻塞 | 联系人按需展示，避免数千 DOM；扫描常驻页、有限缓冲区；以 PSS、私有内存、延迟和压力衡量 |
| 画面流畅性 | 自适应可读画质与链路；操作清晰、输入准确；连续使用不堆积延迟 | 在局域网测画面更新、输入与滚动；压缩、损伤检测、编码方案须比较后采用，不随意丢弃协议数据 |
| 系统稳定性 | 切账号不串数据；人工输入优先；后台任务互斥且能退出 | 身份守卫、取消、进程退出、连续开关页面、扫描重复运行、重连测试 |
| 包体积与复用 | 同内容跨架构仅存一份；只携带确有依赖的组件；安装不依赖临时网络 | 依赖闭包审计、离线包完整性、两架构校验；不能靠删输入法、字体、许可证或功能缩包 |
| AI 回复质量 | 针对完整消息轮次回答；主客体、引用、日期、本人信息准确；未知不编造承诺 | 测试本人风格、人工接管、身份开关、群聊分享边界、连续消息及图片。自然表达不能保证所有人无法识别自动回复 |
| AI 成本 | 同信息不重复发送；只带当前任务需要的记忆；输出长度与实际聊天一致 | 记录请求字符与服务返回 token；保持归属、隐私及发送安全规则。缓存或截断不得损害回答准确性 |
| 隐私与维护 | 密钥不落日志；账号隔离；升级保留数据；结果可追溯、可回退 | 准备升级前备份；保留来源、版本、包和安装后哈希；Git 远端验证与设备验收分别记录 |

## 基线

- 真机：192.168.3.7，x86_64，4 CPU，16GB；当前版本 0.10.20-stable.003。
- 全功能通用安装包：570,674,460 字节；主要体积来自双架构 Linux 兼容运行库，官方微信不在安装包内。
- 12.5 秒空闲采样：栖盒相关进程合计 PSS 约 1,638MiB，其中多数来自官方微信及其子进程；Node 约 114MiB。此数据不能当作密钥扫描峰值。
- 自动化基线：970 项 Node 测试全部通过。
- 我的信息：17 个可选字段、逐项分享、建议确认及历史恢复已有实现；本轮保留这些语义。
- 联系人：当前 Bot 账号 1,604 联系人、333 群；当前列表全量创建行。

## 多轮比较与完成条件

1. 第一轮：修复扫描冷页读取和前端大列表、改善个人信息编辑与保存；使用合成数据及真机读操作比较。
2. 第二轮：去掉 AI 上下文重复信息，依赖闭包和跨架构包复用优化；比较回复正确性、请求大小及安装包差异。
3. 第三轮：实际安装、微信与 AI 全流程检查、连续交互与资源采样；针对失败再修复并重验。

每轮记录采用与放弃的方案及原因。最终交付必须分别列出：源码测试、包完整性、fnOS 应用中心安装、真实微信/AI 操作、ARM64 验证边界、远端 Git 状态。没有真实 ARM64 设备就不能声称 ARM 真机通过。

## 多轮优化结果

- 第一轮：真实 Bot 数据预览，联系人列表从 1,604 行减到首屏 18 行，末尾仍可通过键盘到达；搜索在完整数据上运行。手机 390px 页面无横向溢出，保存入口可见。预览仍使用 0.10.20 真机后端，不作为新包安装证明。
- 第二轮：NAS 上用 100,000 条合成消息比较旧、新 worker。旧代码空闲 RSS 为 79,495,168 字节且仍持有上次结果；新代码为 21,790,720 字节且结果已释放，约降低 72.6%。处理峰值两者均约 121MiB，不能据此声称峰值也降低。该项是硬件上的合成负载，并非真实用户聊天导出。
- 真正的输入阻塞：只读扫描和数据库队列退出人工输入等待链；会修改微信窗口、发送及清理草稿的队列继续保持互锁。专项回归覆盖只读请求未完成时输入可继续，以及未清理草稿的 Enter 仍被阻止。
- 冷会话扫描：当前测试进程已使用过，常驻页遍历只减少约 2.5% 读取量，冷定位仍约 4 秒；此样本没有显示内存峰值收益，不夸大效果。保留跳过未分配页机制，并对新版本动态发现的布局增加受进程、账号、可执行文件、时间和实时结构校验约束的私有提示复用；不能以提示替代发言身份校验。
- AI：完整原文只发一份，重复摘要和来信索引改为引用，风格不同时重复在系统正文和输入中。只改发送格式，本地归属校验保留完整原文；新增请求字符和实际接口 token 的无内容诊断计数。实际回复、监控知识提取、原消息来源恢复均已在模型与安装版检查；token 结果按含缓存的完整输入统计。
- 缩包试验：静态 ELF 依赖表发现 `fcitx5-pinyin -> QtWebEngineWidgets`、`libavfilter8 -> libflite1`；因此保留这些输入法和媒体依赖。保留原始载荷哈希、许可证与双架构共享复用；额外交付适配此 x86_64 NAS 的单架构包，移除服务器未用的浏览器 PDF 构建和 JS 调试映射，并比较压缩等级。
- 发布前源码回归：990 项 Node 和 299 项 Python 单元测试通过；这些不是物理手机、屏幕阅读器或 ARM64 真机验收。


## 最终选择与放弃方案

| 选择 | 依据与实际结果 | 边界 |
| --- | --- | --- |
| 保留原生微信和现有远程桌面，先修复人工输入被只读任务排队阻塞 | 联系人首屏 18 行；人工输入与只读扫描解耦；中文、emoji、原生 @成员、全屏、重连及 AI 五个页面在真实安装版可用 | 未更换视频协议；未完成跨公网网络与所有物理手机的流畅性认证，100ms/P95 属于目标 |
| 分块读取、受校验提示复用、限制快照和释放上次结果 | 真机合成消息处理后 worker 空闲 RSS 降 72.6%；Node 大结果合成接收耗时 1311.6→31.8ms、进程最高 RSS 207.6→116.8MiB | 两项是不同合成基准；实际冷会话扫描约 4 秒、峰值未证实下降 |
| x86 专用离线包与通用包同时保留，兼容依赖按内容复用 | x86 368,959,335 字节，比原通用包小 35.35%；通用 566,674,109 字节，比原通用包小 0.70% | 35.35% 来自架构选择与少量精简的组合，不能宣称同架构包缩小 35%；ARM64 未在硬件安装 |
| 原文与身份保留，发送时仅复用重复内容和长编号 | 一组缓存口径一致的对照，主请求输入 17,510→10,853；计入全部复核请求后 20,652→17,188，输入减少 16.8% | 复核及重试不能删；样本输出 1,038→4,224 token，费用不能仅凭输入降幅推算 |
| 监控知识输入同样使用短编号并明确提取协议 | 同一虚构事实测试：输入 3,875→2,417，减少 37.6%；旧结果为空，新结果提取成功；安装版再次提取并合并成功 | 使用已配置的真实模型与隔离资料库，没有把虚构事实写入真实联系人 |
| 个人信息紧凑卡片、按需展开、固定保存区 | 17 个字段完整保留；草稿跨页面保留；清空到原值后保存按钮禁用；逐项分享、建议与历史流程保留 | 320/390/1024/1440 是浏览器视口测试，不能称物理手机验收 |

未选择删除字体、输入法、媒体依赖或远程微信功能来缩包；QtWebEngine、Flite 等存在实际依赖。未选择把现有原生微信替换成自行实现的聊天客户端，也未以隐藏核验步骤换取更低 token。视频协议更换需要独立兼容性和弱网比较，本轮缺乏支持其优于当前方案的实测依据。

## 修复迭代与真机验收

- `.001` 至 `.005` 连续五轮均实际通过飞牛应用中心升级；最终交付 `.005`，应用源码提交 `7cf329332b8c3f4b4da1f34cd717e58e65a9a733`。
- 最终应用中心任务 `1790884529294994074-qibox`：status=2、progress=100。x86 安装目录全部 2,015 个文件哈希与最终包的构建目录一致；通用包独立核对 2,394 个文件。
- `.003` 私聊与真实 @群聊各完成一轮，原生数据库与双方微信画面一致，方向正确、未重复发送。私聊收到“常看的放顺手那层，大概跟视线平齐或者腰部高度，拿起来不用踮脚弯腰。🙂”；群聊收到“眼平那层最顺手 不用低头也不用抬手”。关闭承认 AI 身份时，普通接话未主动说明自动回复身份。
- 第三轮私聊中检查者切换聊天窗口导致首次发送取消；守卫随后重新判断并完成一条发送。该轮整体约 98.2 秒（含重新判断），最终模型约 9.9 秒、原生发送约 18.2 秒。群聊整体约 35.2 秒、模型约 6.1 秒、发送约 19.2 秒。AI 等待和自然发送节奏不能当作页面操作响应速度。
- `.002` 人工回复后的 3 分钟 AI 等待自然完成，未跳过等待；实际回复只发一次。早期跨页面极快粘贴后立即 Enter 曾出现乱码；重新连接后，同页快速中文+emoji 粘贴与发送、草稿全选清空、复制回浏览器均通过。未复现全部跨页面竞态，不能据此保证任何速度下都无问题；物理 Windows 剪贴板未认证。
- 六类实际模型重放涵盖建议、本人引用、多问题、群内他人引用、未知安排及本人旧话+对方新事件。根据失败补上无依据本人习惯、虚构后续通知、遗漏轮次及复核协议一次修复。最终六类均得到有效结果，其中本人引用首试外部模型超时，单独重试通过；超时不计为通过。
- 最终监控知识使用安装目录真实模块、用户已配置的学习模型，在隔离资料库确认事实、原始 64 位消息编号和观察时间保留。真实账号个人信息仍为空，未保存虚构资料。
- 1,618 个对象的测试设置核对恢复，其中 1,616 个非测试对象恢复原暂停状态；两个受控对象恢复原回复、群聊及记忆设置。全局开关、范围、选定列表恢复；测试历史、计数与已处理游标保留，避免重发。服务重启后两个受控账号仍正常登录，原未登录实例没有登录。

### 第四、五轮补充验收

- 第四轮实测发现：关闭承认身份后，复核模型可能把中性的回应改成间接承认 AI。身份策略现在同时传入生成与复核，且仅在当前来信询问身份时生效；防止旧问题、引用、普通接话错误触发。第五轮安装模块真实模型结果：关闭时“怎么突然这么问？”，开启时“是AI代回复的，抱歉之前没说清楚。”；不允许伪造本人正在亲自输入等证明，也不保证任何人无法识别自动回复。
- 第五轮修复监控知识的嵌套协议校验：错误地把来源编号写进 newMessageIds 而非 evidence 时，整轮明确失败并保留学习进度，不再静默丢弃事实。990 项 Node 回归包含错误返回后进度不前移、重试后正常合并。安装模块真实模型提取虚构宠物事实，并在独立临时资料库验证原始编号、观察时间与合并结果；不写入实际联系人。
- `.005` 真实私聊收到“第二层正合适，视线平齐拿取最顺手，不用踮脚也不用弯腰。🙂”。首次定位微信控件暂不可用，自动重试后实际送达一条；最终模型 12.4 秒、发送 11.3 秒，整体 101.6 秒含首轮失败和等待。旧失败 notice 值在重试后仍保留，最终页面未出现错误遮挡，恢复设置并重启后清除；不将此轮描述为零失败或即时回答。
- `.005` 真实 @群聊收到“伸手就够到的地方 比如笔筒放右手边 不用站起来拿就行”。整体 35.9 秒，模型 8.2 秒、发送 18.5 秒；双方数据库和接收画面确认同一正文、正确方向，各一条。以上属于受控测试，不是所有联系人、网络和媒体场景的穷尽验收。
- 实际书架私聊没有新增长期记忆：本轮回复模型没有输出记忆更新，回复流程完成后游标已推进。隔离监控模型提取通过与实际聊天自动留存是两种证据，不能把前者当作后者。本轮不保证每一句新事实都会被记住；明确资料仍可由用户在个人信息中维护。
- 第五轮卡片在真实安装版再次检查，17 个字段、折叠与常驻保存区保留，真实个人资料为空且无待保存草稿。最后核对恢复 1,618 个对象的原配置，全局设置相同、历史与计数保留。重启后的首次过早状态检查暂为 logged-out，页面重新连接后两个账号均 logged-in，原未登录实例保持 stopped/logged-out。
- 最终包：x86 SHA-256 `067ea0108e0d1e2cfca509b49b5e13fd2da8a4b5b5f3a41bce9d75de3e46e828`；通用 SHA-256 `98ac47feec95a30b8ca21ada2ecc18109be6f48cecabd11203896044534454e4`。安装后 2,015 文件一致；ARM64 只做包与文件校验。

## 内存的实际结论

第五轮设置恢复并确认两个账号登录后五次约 12 秒采样，相关进程 PSS 合计约 2,022–2,049MiB；官方微信主进程和 WeChatAppEx 平均约 1,448MiB，栖盒 Node 约 137MiB、数据 worker 合计约 54MiB。可用内存约 10.33–10.37GiB，采样内存压力 avg10/avg60/avg300 均为 0。

基线与最终采样的打开窗口、账号和执行负载不同，不能以 1,638MiB 基线与最终总值计算整机优化降幅。已证实的是集成模块分配有界、大结果持有减少、人工输入不再等只读队列；没有证据证明官方微信总体内存或密钥扫描峰值下降。强行限制官方微信可能造成重载、输入延迟和稳定性损失，本轮未采用。

## 对照资料与证据等级

字节缓冲方案参考 [Node.js Buffer 文档](https://nodejs.org/api/buffer.html)，页面驻留位参考 [Linux pagemap 文档](https://www.kernel.org/doc/html/latest/admin-guide/mm/pagemap.html)。UI 的 WCAG AA 是验收目标，本项目主要触摸操作采用 44px 目标；[W3C 2.5.8 最小目标尺寸](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)规定的 AA 最小尺寸为 24 CSS px，不能把 44px 与全面 AA 认证混为一谈。

本地回归、合成压力、NAS 应用中心安装、真实微信收发是分别记录的证据。全量长期稳定性、所有微信操作、屏幕阅读器、物理手机、Windows 系统剪贴板与 ARM64 硬件尚未完成穷尽验收。此方案是本轮多次比较后通过已列验收的交付方案，不宣称所有设备和网络条件下的绝对最优。
