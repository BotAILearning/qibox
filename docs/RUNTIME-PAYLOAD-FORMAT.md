# 单个双架构安装包的共享运行时

格式 3 继续交付一个 `all.fpk`。两架构保留原始 Debian 组件清单和 SHA-256 来源；文件内容、权限与链接相同的项目集中保存一次，其他项目只进入其对应架构的归档。设备依次展开共享归档和本机架构归档。

`prepare-runtime-solid.py` 按原组件顺序计算最终文件树，沿用旧准备脚本对 man、changelog、NEWS 的清理规则。第一轮不删除运行组件、字体、输入框架、词库或媒体功能。每份成品归档重新解码并核对全部成员；可能改变内容的硬链接覆盖关系会被拒绝。

`payloadFormat: 3` 使用 `archives` 描述实际展开对象，`packages` 保留源组件来源。旧格式仍由同一加载器支持。运行时指纹包括归档清单，升级会构建新的 `.preparing` 目录，再发布到正式目录；不会靠旧文件残留补齐依赖。`verify-fpk.py` 核对两种架构的来源、所有引用归档、版本、成品内容及未引用归档。

首轮以 `0.10.30-stable.001` 为基线：848 个组件引用，归档由 803 份变为 3 份，压缩运行时为 513,789,432 字节。完整 FPK 的体积变化和正式安装结果由对应发版验收记录提供，不能使用归档字节代替整包大小。

后续裁剪必须单独记录消费者、动态加载路径及真实微信行为。Fcitx 拼音词库设置模块确实依赖 Qt WebEngine；FFmpeg 也仍依赖其编解码与过滤库。没有正向使用记录不能证明组件可删。缺少另一架构的硬件证据时，不能把 x64 真机结果标成 ARM64 已通过。

第二轮的 `config/runtime-policy.json` 按路径、内容 SHA-256、模式及链接锁定 x64 的 27 项可选词库管理设置窗口依赖。当前产品没有该设置窗口入口，保留 Fcitx 主程序、拼音引擎、词库、GTK 接收模块、基础 Qt 窗口组件。构建器拒绝来源漂移、剩余 ELF 消费者及仍指向删除项的链接；真机额外核查当前单独安装的微信及其 106 个程序/库的依赖、嵌入动态名称和进程映射。ARM64 不应用该裁剪策略。

x64 归档使用可逆 x86 分支过滤和 LZMA2 9e；重解码后仍逐项核对内容、权限与链接。按每组清单哈希和压缩策略复用成品，避免未变化的共享及 ARM64 归档反复构建。其他压缩实验先核对整个解码 tar 的 SHA-256，再比较实际归档和完整安装包体积；只有较小且内容相同的结果才可晋级。
