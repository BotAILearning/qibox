# 分析报告与历史记录实施方案

## 目标和边界

用户已授权规划后交给 Luna 实施，部署飞牛真机 192.168.3.7，测试通过后打新包。名称统一为「分析报告」，按用户选定时间范围分析；借鉴音乐回顾的短章节、大数字、真实片段与温暖叙事。详细方案与精炼模型提示词分离。保留现有用户自定义分析要求。UGOS 不在本次范围。

## 用户流程

1. 现有聊天分析页选择联系人、时间范围和可选分析要求，点击开始分析，每位联系人独立处理。
2. 成功报告自动持久保存，立即展示；历史记录入口始终可见，即使联系人当前不可读取也可查看已保存报告。
3. 历史记录按生成时间倒序，展示联系人、实际记录起止时间、生成时间、分析消息数和简短摘要，支持打开、复制、删除。按当前实例及微信账号隔离。
4. 查看历史报告读取生成时快照，不再次调用模型；重新生成属于新报告，不能覆盖旧报告。
5. 点击删除先弹确认框，说明仅删除该份报告、不会删除微信聊天记录，提供「取消」「删除报告」。取消、Esc、关闭均不删除；确认后服务端删除成功才更新列表，失败保留条目并提示。删除当前查看报告后返回列表。

## 内容与呈现

- 页首固定「分析报告」和联系人、时间范围，范围由程序根据请求及真实记录计算；全部必须具体到记录日期，模型无须承担日期边界计算。
- 短章节顺序：数据开场、聊天节奏、主要话题、互动特点、值得记住的片段、收尾。主题随数据自然变化；依据不足的章节可省略。
- 章节标题短、正文约 60–140 字，通常 4–6 节，优先具体事情和证据，不堆砌泛泛抒情。自定义要求优先，可展开必要细节。
- 程序计算消息数、双方消息量、活跃天数、时段分布等可靠统计；数据卡突出数字，章节有层次，沿用现有深紫色 UI，兼容移动端自然滚动。
- 引用仅采用原始消息中可验证的短片段；不凭消息量推断爱意，不把缺失图片语音解释为事件。分块汇总保留来源，不把各分块频次相加当作全量统计。
- 读取截断或不可解析消息需显示覆盖范围提示，不能声称分析了全量。空数据、模型失败不生成伪成功历史。

## 精炼提示词核心

请根据用户选择的时间范围生成分析报告，优先满足用户的分析要求。以音乐回顾式的节奏，将真实数据、具体洞察和聊天片段组织为有层次的短章节：数据开场、聊天节奏、主要话题、互动特点、值得记住的片段和收尾。用「你」与「对方」讲述，温暖克制，每章围绕一个发现展开，避免流水账和空泛抒情。只使用给定统计和聊天证据，引用须与原文一致，依据不足的内容省略。

注：现有消息时间解释、资料不作为指令、分块处理以及 JSON 协议等技术约束继续在服务端维护，不放入用户输入框。可保留兼容 report 字符串并添加程序提供的 metrics/日期元数据，避免无必要扩大模型协议。

## 持久化与接口

- 每份成功报告保存不可变快照：schemaVersion、id、实例/账号作用域、联系人 id/展示名、createdAt、requestedRange、实际记录范围、用户要求、count/skipped/truncated、metrics、报告正文及必要章节信息。
- 按当前项目存储惯例落盘，原子写入；列表仅返回摘要，详情按 ID 获取，删除在当前账号作用域内解析。限制 ID 和路径，避免跨账号和任意路径访问。
- 生成完成后先保存，再返回成功；保存失败明确显示原因，不提示已进入历史。账号切换、取消及并发请求时仍执行既有 revision/account 检查，防止串号。
- 不使用 localStorage 作为唯一历史来源；重启应用、刷新页面后仍能查看。旧版无历史数据能直接启动。

## 实施与验收

Luna 负责源代码和有价值的测试，我负责方案、部署基线检查、复核及交付协调。当前本地为 0.8.6-debug.005，最终版本结合现有交付与真机核验后确定，旧包不覆盖。

必须覆盖：选定范围/全部的实际日期；多联系人不混合；真实数字与长记录分块；空记录/模型失败；成功保存；刷新及服务重启后查看；同联系人多次独立历史；取消删除和确认删除；删除失败；账号隔离；手机宽度；旧有分析要求仍可用。

先 SSH 核验真机与本地差异并保存备份，保留既有真机修改和账号数据。部署仅本批必要文件，验证服务健康、真实分析生成到历史持久化闭环及浏览器删除确认。只能删除本次测试新建报告。禁止测试发送真实微信消息。通过后构建 fnOS FPK，校验包内容、版本、哈希和源码一致性，记录实际测试边界。
