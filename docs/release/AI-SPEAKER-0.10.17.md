## 修复内容

用户反馈自动回复会把本人发言当成对方发言，也会把对方发言说成本人说过的话。本轮用两个受控账号核对同一条原生微信消息：发送账号读取为 self，接收账号读取为 other；原始消息方向一致。问题集中在提供给模型的上下文、摘要和回复视角，而非需要整体翻转微信读取方向。

- 以已校验的消息方向、当前账号、联系人及群成员标识确定发言人，不能用正文中的“我”“你”或传入的自述标签改写归属。系统消息、身份未知的消息保持相应状态；身份不明的群成员不能合并成一个人。
- 本人历史以 assistant、对方历史以 user 传入聊天模型，并明确“回复中的我”为当前微信账号本人。保留群成员及引用、转述的说话者；AI 之前代发的话仍属于本人发言，但其中没有确认依据的个人事实不能自动变成本人资料。
- 等待批次、最新消息、最近本人发言、待回复摘要、群聊触发和主动聊天使用一致的发言人信息。最新消息作为索引，仍回应等待期间的问题；末尾“好的，谢谢”不会取代前面的问句。旧摘要里含义不明的“我”不能覆盖原始消息归属。
- 修复延迟处理和旧待回复记录的方向恢复：只从可信来信记录恢复对方方向，拒绝与已知本人或系统方向冲突的记录。
- 所有回复和主动聊天的发送草稿增加独立模型检查，核对谁说、谁问、谁答、谁提出及事实归属。需要更正时，修正稿经过原有业务校验，再独立检查一次；仍冲突或返回格式无效则保留待回复，不发送未核验内容。保留原有续聊等控制字段，文字仍限制整轮 1–5 条。

通常每轮发送比此前多一次模型请求；需要更正时还会检查修正稿，因此可能增加模型用量与等待时间。该检查用于降低已发现的归属错误，不保证模型永远不出错。

## 真机 MiniMax 场景

通过 NAS 上实际配置的 MiniMax-M3 发起真实模型请求，使用虚构对话夹具，12 个发言归属场景通过。此项没有向微信发送测试夹具消息。

| 场景 | 已验证结果 |
| --- | --- |
| 各自所在城市 | 对方苏州、本人杭州，无反转 |
| 各自宠物 | 本人猫豆包、对方狗丸子 |
| 谁提出及谁更改日期 | 本人提周六、对方改周日、最终周日 |
| 对方工作状态与本人休息状态 | 不把对方开三场会说成本人经历 |
| 引用本人原话 | 引文中的“我”正确归于本人 |
| 转述第三人 | 第三人的兔子不归于本人或对方 |
| 来信语音转成的文本 | 转写内容仍属于来信方 |
| 群聊两个成员 | 两人的城市与本人的城市分开 |
| 旧摘要中的第一人称 | 原文归属优先于含义不明的摘要 |
| 私聊待回复摘要 | 用“对方”描述来信事实 |
| 群聊待回复摘要 | 分开保留两个成员及事实 |
| 主动问候对方宠物 | 询问对方的狗，不把本人的猫当成对方宠物 |

示例实际返回：“你住苏州，我住杭州，没记反。”以及“最早我提的周六，你提的周日。最后定周日。”。人工复核与预设归属断言一致。语音项是转写文本场景，本轮未声称完成新的原生语音硬件收发验收；主动聊天仅验证上述任务，未声称覆盖所有复杂任务。

## 原生微信与安装验收

两个受控账号使用实际微信 4.1.13.23 原生输入、官方群成员提及选择器及正常发送操作；未向第三位群成员或其他联系人发送测试消息。

| 阶段 | 对话 | 结果 |
| --- | --- | --- |
| 候选源码 | 私聊，引用停车与素菜旧问答，最后一条致谢 | 明确原话是本人回答，对方提出两个问题；1/1 确认送达 |
| 候选源码 | 群聊，实际 @本人 后补充谁问集合时间和入口，最后致谢 | 明确对方问、本人答；1/1 确认送达 |
| 应用中心安装 0.10.17 后 | 私聊，再核对是谁问、谁答，最后致谢 | 两个问题与回答均正确归属；1/1 确认送达 |
| 应用中心安装 0.10.17 后 | 群聊，完整 @本人 问句及补充，最后致谢 | 明确对方问、本人答，@本人已由原生消息确认；1/1 确认送达 |

四轮共核对 16 对双账号原生消息，8 对私聊、8 对群聊，方向不一致数为 0。安装后私聊模型阶段约 9.1 秒、群聊约 6.0 秒；这些是本次特定样本，不是性能保证。群聊等待批次的三个消息间隔在 8 秒内，回复仍回答早先问句。

候选私聊初次等待较长源于测试脚本未加入回复对象，补上受控对象后原有消息正常处理，未重发消息。候选群聊脚本仅成功发送提及，问句由后续补充发送，未把未发送的首条完整问句算作证据。安装后群聊准备阶段出现原生退出确认弹窗，已取消，账号未退出；清除重复草稿、确认官方成员提及后才发送并完成最终核验。以上属于验收脚本准备问题，未改微信数据或把脚本问题计作产品归属问题。
