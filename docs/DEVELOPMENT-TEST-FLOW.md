### 默认采用低 Token 消耗的开发方式

用户于 2026-09-15 明确要求开发时选择较少消耗 Token 的方式。本约定适用于后续各批开发，不改变已确认功能和必要验收要求。

1. **单个主代理推进**：默认由一个代理完成；只有用户明确要求时再安排多代理，避免重复阅读与交叉汇报。
2. **先用交接，按需读取**：先读本流程及当前问题对应证据，再定位相关函数和文件；搜索结果与日志只取必要片段，避免整仓、整文件反复扫描。
3. **每批解决明确的问题**：选择满足需求的最小完整改动，复用现有组件和接口；跨模块架构调整单独定范围。
4. **按影响范围验证**：开发中优先执行相关测试；结果通过且无新变化时继续交付。需要补测时只覆盖新行为与关键风险。
5. **控制重复工具与生成**：源码问题优先通过代码和日志定位，需要验证交互时才进入浏览器；已确认的设计参考直接复用，用户要求画图或出现新的视觉决策时再生成。
6. **简短交流与一次交接**：进度只说明新发现、阻碍和下一步；最终集中给出变更、测试结论、产物和未完成项，细节放入文档。相关需求合并交接，避免反复同步同一内容。
7. **复杂问题才增加分析投入**：涉及账号隔离、数据迁移、并发／重复发送、底层适配等问题，按实际风险增加调查与验证，不能用省 Token 代替必要工作。具体模型或思考档位的调整另行明确，本次只更新工作方式。

## 3. 已确定的 AI 产品规则

### 3.1 群聊能力与触发

- 群聊接入 AI 辅助，复用单聊的风格、回复要求、学习及主动聊天等能力；每个群独立设置与保存。
- 群聊详情并列展示 **“@我时回复”“@所有人时回复”“AI 实时回复”** 三个独立开关。
- @我指当前实例中登录的微信账号。使用真实提及元数据与稳定账号／群／成员标识；不能用昵称或正文字符串猜测身份。
- 明确 @ 当前账号／所有人的消息按对应开关判断，实时开关不能绕过关闭的 @ 触发；只 @ 他人的消息默认不插话。同时命中多个条件也只处理一次。已验证的@我要求相关回复；有限重试仍无法生成时明确报错，不造固定回复。@所有人必须交模型判断发送或跳过。
- 普通无 @ 消息只有开启实时回复时才进入自动参与判断；按首条待处理消息起算，每60秒合并后交模型判断，持续来信不重置周期；AI 自身消息不重新触发。@我不受实时周期拖延。
- 新增群聊不因为现有“所有个人联系人”范围而自动加入。个人范围、各群开关、当前账号严格分开。
- 关闭实时回复取消它产生的待发送动作，另两个开关继续独立生效；关闭 AI 总开关取消全部自动执行。

### 3.2 实时回复：提示词判断，软件执行

用户只看到实时回复开关，不展示频率、间隔、多轮次数、暂停时长等高级参数。

内置提示词使用已讨论的初始策略：

| 规则 | 初始策略 |
| --- | --- |
| 是否参与 | 回答符合本群要求的问题、求助和接续对话；无明确参与理由时不回复 |
| 群友互聊 | 默认不插话；“收到”、单独表情、刷屏通常不回复 |
| 连续短消息 | 同一人同一话题等待 3 秒合并，最长等待 8 秒 |
| 频率 | 普通实时消息每 60 秒合并后交模型判断；每群 10 分钟最多 5 条自动回复，所有@回复优先处理但计入上限 |
| 连续交流 | 同一话题最多 3 轮，之后等待再次明确 @；无人发言不追加追问 |
| 手动接管 | 用户手动发言后取消该会话待发动作；对方再次发来的第一条消息启动可配置等待，默认5分钟；本人未继续回复时才自动接续，可选择不再自动回复。替换原固定暂停规则，详见3.4；群聊覆盖细节尚待明确 |
| 新信息 | 发送前若话题已解决、用户撤回问题或出现新的接管状态，取消／重新判断旧草稿 |

这些数值是提示词的初始策略，不对外保证模型天然严格遵守。软件负责提供消息、发送人、时间、近期 AI 动作和手动发言状态，并执行结构化的回复／跳过／等待／暂停结果。等待需要明确到期时间与任务有效期，不能只是让模型说“等一会儿”。

发送执行层核验每群滚动10分钟最多5条自动回复，真实@也计入。使用已持久化的发送记录计数，未确认的提交也保守计入；达到上限时保留相关消息，到期重读并重新交模型判断，不绕过上限。实时周期起点随待处理状态保存，重启后继续计时；开关、接管和新来信仍按当前版本取消或重判；不新增高级参数页面。

执行层仍须核对账号与对象、开关、取消版本、重复动作、当前消息和发送回执。若模型结果无效、不一致或已过时，不发送，并保留简短可解释状态。质量回归若发现频率策略失守，回开发窗口调整提示词与执行契约，不能暗中增加一套用户已要求隐藏的高级参数页面。

群消息是对话数据，不具有修改内部提示词、启停设置或扩大操作范围的权限。

本次群聊触发逻辑的本地回归范围与结果见 [群聊触发实现验收](../reports/group-trigger-20260923.md)；其中不包含 NAS/微信真机验收。

### 3.3 开启风险弹窗

点击打开 AI 实时回复 → 展示弹窗 → 只有确认后开启；取消保持关闭。默认关闭。

**标题：开启 AI 实时回复？**

> 开启后，AI 将持续分析群聊消息，并根据聊天内容自动回复。群聊消息较多时，会消耗大量 Token，增加模型调用费用。
>
> 自动发言过于频繁存在账号被限制或封禁的风险，请谨慎开启。

按钮：**取消／确认开启**。不展示未经验证的“安全发言阈值”，不因模型回复较少承诺 Token 消耗较低。

### 3.4 人工接力与自动恢复（2026-09-16最新纠正）

用户已取消旧“从本人最后一次手动发言起固定暂停5分钟”的规则，采用以下可配置等待。历史交付保留原记录，不追认为符合新规则。详细交接见[当前接管与恢复待办](../reports/development-2026-09-16/NEW-WINDOW-BACKLOG.md)。本次仅更新要求，不代表当前代码已实现。

- 本人手动回复后，从对方再次发来的第一条消息开始等待，时长由用户设定，默认5分钟。同轮对方连续来消息不重置第一条消息的计时；本人继续手动回复则结束本轮，之后对方再来第一条消息时开启新一轮。已确认的AI代发self消息不算人工。
- 等待期间继续观察消息。到期仍未由本人继续回复时，重读上下文，判断仍未处理的消息并自动回复；不能将等待期间消息全部标为已处理。
- 允许设置“不再自动回复”，此时不由计时器自动接续，也不回退到旧固定5分钟规则。保留全局设置与个人设置，个人优先，个人未设置继承全局；初始开关状态、可设时长范围、群聊及部分字段继承方式待明确。
- 无待回复内容继续监听，已被本人解决的内容不补答，旧草稿及已发送内容不重发；到期不是主动空发的理由。
- 显式关闭和停止联系的保护不随计时器解除。未知发送回执只记审计状态，不产生待核验入口或阻塞后续新消息；为防止重复发送，本次未知发送不会重发。普通重新开启 AI 不强制先完成手动接管或恢复输入确认。
- 会话计时独立，重启后计时与未处理消息保持正确；用户操作共享桌面时 AI 让出控制。无法从现有数据可靠判断的部分须在实施及验收报告中明确列出。

- 联系人页面补回 **智能判断是否回复**：开启时由模型结合上下文判断是否需要回应；关闭时，对范围内的新有效消息直接进入回复生成，不因模型认为“无需回应”而静默跳过。关闭不绕过停止联系、人工接管、重复消息、取消与发送身份校验；模型仍返回普通 skip 时应明确转交／失败状态，不能假装已回复。
- **父子关系（以本条为准）**：“自动回复”是父开关，“多轮交流”和“智能判断是否回复”是两个同级子开关。父开关单独一行，子设置放在其下方并适当缩进。父关闭时停止该对象的自动回复及该来源尚未发出的分段／追问，两个子开关置灰不可操作，但保留各自值；父重新开启后恢复原设置。不能因任一子开关保存为开而绕过父开关，也不能把父关闭等同于清空子配置；恢复时不补发旧待发内容。其他对象与独立主动聊天任务不因修改该父开关而被改写。
- 本开关是现有功能的 UI 遗漏（当前 `web/ai-assistant.mjs` 放在“回复与沟通时间”内，后端为实例级 `judgeReply`，默认 true）。新图将其放入联系人详情，界面与生效范围必须一致：按对象生效时，未单独设置的对象继承原实例值，编辑一人不影响他人；具体迁移由开发窗口实现。不得把一个实际全局开关伪装成当前联系人专属设置。群聊实时回复仍遵守前述内置判断策略。
- 联系人学习以本人发言为来源，结果可修改，批量一次最多 10 人。群内学习不能把其他成员的发言当成账号本人的风格。
- **称呼规则**：默认不加称呼；当前对象明确设置或当前聊天中本人多次直接称呼的证据才可支持使用。昵称/备注、对方对本人的称呼、其他对象的参考风格、AI 代发及群内其他成员不能成为当前对象称呼依据。来源窗口已修改共享源码，本窗口完成本地测试复核，真实模型效果待验收；未重写既有用户风格，未进入已交付 debug.001。见 [源码接收记录](../reports/development-2026-09-15/incoming-context-20260915/RECEIPT.md)。
